## אחריות התיקיות הקיימות

- `public/`: המסכים, העיצוב והתנהגות הדפדפן. דפים נפרדים למטופל, לצוות ולמנהל הם הפרדה תפקודית תקינה.
- `public/app.js`: קוד דפדפן משותף, גישה לנתונים, אופליין ועזרי API. זה הנתיב הנכון; `public/js/app.js` אינו הנתיב במבנה שנבדק.
- `public/js/shared/`: התנהגות משותפת לתיעוד ביקורים. לבדוק שימוש חוזר לפני יצירת קוד נוסף למנהל ולעובד.
- `public/js/admin/`: חלקים של מסך הניהול המחולקים לפי אחריות.
- `backend/app/`: שרת Python תפעולי — הזמנות, שיבוץ, הרשאות, זמינות ומעברי מצב. המודולים הקיימים כבר מפרידים בין HTTP, שירות עסקי, חישובים וגישה ל-Supabase; אין צורך לשכתבם לצורך סדר בלבד.
- `predictive-service/`: חישובים קליניים, תחזיות ותשתיות מודלים. אין להעביר לתוכו את כל לוגיקת ההזמנות ואין לשנות נוסחאות לצורך ארגון קבצים.
- `supabase/migrations/`: היסטוריית המיגרציות. אין לשכתב היסטוריה שכבר הוחלה כדי שתיראה נקייה יותר.
- `supabase/proposed/`: מקור ה-SQL שהוחל על הפרויקט ב-2026-10-15 (ר' APPLIED.md); הועתק גם ל-`supabase/migrations/` עם הגרסאות הרשומות. משמש גם כקלט לבדיקות האימות.
- `backend/tests/`, `backend/tests_db/`, `tests/`: בדיקות בשכבות שונות. בדיקה על stub אינה הוכחת אינטגרציה עם Supabase Auth ו-PostgREST אמיתיים.
- `docs/`: מסמכי עבודה, תכנון ותמונות. יש להבחין בין הנחיות פעילות למסמכים היסטוריים ולתוצרי preview.

## זרימת האחריות הרצויה

מסלול תפעולי: דפדפן → backend Python → Supabase, עם אכיפת הרשאות ושלמות נתונים במסד.
מסלול קליני: רכיב מורשה אוסף קלט → שירות החיזוי מחשב → התוצאה חוזרת למסך או נשמרת במסלול מורשה.

שירות חישובים אינו חייב חיבור ישיר למסד כדי להיות תקין. כן נדרשים חוזה קלט/פלט ברור, הרשאות, טיפול בכשל והגדרה מי מביא ושומר נתונים. אין לדרוש אוטומטית שכל פעולת Supabase בפרויקט תעבור ל-Python; כל העברה צריכה סיבה ונתיב שרתי מוגן.

## שימור מודלים

מצורף `MODEL_PRESERVATION_BASELINE.json` עם fingerprints של קבצי `predictive-service/` המנוהלים ב-Git ושל קובצי joblib קיימים שנמצאו בשורש תיקיית models בזמן הבדיקה. ההשוואה בין GitHub main שנבדק לבין שני הקומיטים המקומיים לא הראתה שינוי בקוד predictive-service. זו אינה קביעה לגבי כל ההיסטוריה של הפרויקט או לגבי קבצים שלא נכללו בבדיקה.

- `main.py`: API וחישובים קליניים, לרבות מנגנון תחזית אדפטיבי.
- `clinical_baseline.py`: חישובי קו בסיס, מגמות וחריגות.
- `timeseries.py`: מימוש ARIMA. סף שמונה נקודות הוא תנאי תוכנה קיים, ולא הוכחת תוקף קליני.
- `ml_targets.py`: תשתית אימון וחיזוי ל-Logistic Regression, Decision Tree, Random Forest ו-KNN. קיום פונקציית אימון אינו מוכיח שקיים מודל מאומן או מאומת.
- `lstm_interface.py`: שלד מפורש למימוש עתידי. שומרים אותו ומתעדים את מעמדו, בלי להציגו כמודל פעיל.

אין למחוק רכיב משום שאינו מחובר או אינו מאומן. איחוד קוד מחייב לזהות הבדל התנהגותי ולשמר יכולות וממשקים. אין למחוק נתוני אימון או weights כחלק מניקיון.
