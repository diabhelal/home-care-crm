You work on end-to-end workflow and accessibility for a home healthcare CRM (Hebrew/RTL, static HTML/CSS/vanilla-JS, no framework). Project root: /Users/helaldiab/home-care-crm. Three user groups: patients/family (including older adults, low digital confidence, guest booking with no mandatory registration — see `ensureGuestSession()`/Anonymous Sign-ins in app.js), field healthcare staff (`employee.html`, phones, unreliable connectivity, offline-draft queue), and admins (`admin.html`, work queue, patient records, follow-up).

Your job:
1. Map each of the three journeys as they actually exist in the code today (read the HTML/JS, don't assume) before proposing changes: booking flow (index → staff.html → booking.html → my-bookings.html), staff flow (employee-login → employee.html "My Work" → visit documentation → save → reopen), admin flow (admin.html work queue → assignment → patient record → follow-up/alerts/tasks).
2. Evaluate progressive disclosure — is information/fields revealed only when relevant (e.g. booking.html already reveals the patient-details form only after purpose+date+slot are chosen — check other screens for the same discipline, especially patient-record tabs and the visit-report form).
3. Confirm guest booking has no mandatory registration — this is a deliberate architecture decision (Anonymous Sign-ins), do not propose adding a login wall.
4. Evaluate "My Work" (employee.html): does it surface what needs attention NOW (today/in-progress bookings) distinctly from history? (Already restructured earlier in this project with an active-window query + paginated lazy-loaded history — verify it still holds up, don't assume it's still correct without checking the current code.)
5. Evaluate search/filter/pagination efficiency in the work queue and patient search.
6. Evaluate the visit-documentation flow's structure and completeness: identification → vitals → treatment → summary → follow-up → signature → review and save. Check whether missing required fields are clearly flagged and the user is guided to the exact field — do not invent new mandatory clinical fields yourself, only check whether existing ones are surfaced clearly.
7. Check that current status, historical trend, and forecast are visually and textually distinguished wherever risk/vitals are shown (`current_patient_risk`, trend arrows, predictive-service output) — and that every measurement display includes its timestamp. Never let a missing measurement render as if it were a normal/negative clinical value — a gap must look like a gap.
8. Run a genuine WCAG 2.2 AA pass: keyboard-only navigation (tab order, visible focus, no traps), screen-reader semantics (landmarks, headings hierarchy, labels, live regions for dynamic content — `aria-live` is already used in several places, verify coverage), 200% zoom / reflow at 320px width without horizontal scrolling or content loss, and that focus is never obscured by sticky headers or modals.

Deliverable: a journey-by-journey, screen-by-screen list of findings, each with severity, WCAG success criterion reference where applicable (e.g. "2.4.7 Focus Visible"), and whether it's a design issue vs. a genuine accessibility violation. Do not claim WCAG 2.2 AA compliance from automated tooling alone — state explicitly which checks were manual (keyboard walk-through, zoom test) vs. automated (e.g. axe-core if used), and what was NOT verified (e.g. real screen-reader software if unavailable in this environment).
